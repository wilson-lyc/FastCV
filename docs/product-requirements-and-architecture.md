# FastCV 产品需求与技术架构

## 1. 文档目的

FastCV 是一个浏览器插件，帮助求职者在不同招聘网站和企业招聘系统中快速、准确地填写个人简历信息。

产品围绕两个核心能力建设：

1. **简历数据维护**：让用户建立一份结构化、可复用、可版本化的个人求职资料库。
2. **网页表单智能填写**：识别当前网页表单的字段含义，将资料库中的数据映射到表单，并在用户确认后完成填写。

Jev 不是普通的 LLM，而是 TypeSafe 定义的 System One 模型：向它提供结构化状态和类型化问题，得到程序可以直接消费的类型化决策、概率分布和置信度。它不以自由文本生成为目标，因此不应被用来撰写整段简历、生成任意 JSON 或替用户编造事实。FastCV 将 Jev 用作快速的结构化决策组件：它辅助字段分类、候选排序、风险判断和事实核验，最终阈值、业务组合和是否写入由确定性代码决定；字段内容的读取、格式转换和网页写入也由确定性代码完成。相关模型定位以 [TypeSafe AI 对 Jev 的介绍](https://typesafe.ai/blog/introducing-system-one-models-and-jev) 和 [官方文档](https://docs.typesafe.ai/introduction) 为准。

本文定义产品能力边界、核心交互、数据与模型约束、浏览器插件架构及质量要求，不定义具体开发排期。

其中涉及 CV 字段、字段类型、枚举、敏感级别、版本快照和 JSON 备份格式的具体定义，以 [CV 数据字典](./cv-data-dictionary.md) 为唯一真源；本文档中的能力描述不得被解释为另一套字段定义。

## 2. 产品定位

### 2.1 目标用户

- 需要重复填写多个招聘网站或企业 ATS（Applicant Tracking System）的求职者。
- 同时维护中文、英文或其他语言简历的用户。
- 针对不同职位需要调整项目经历、技能、求职意向的用户。
- 希望提升填写效率，但仍要求自己掌控最终提交内容的用户。

### 2.2 核心价值

- **一次维护，多处复用**：用户只维护结构化资料，不重复手工输入。
- **理解字段，而非机械粘贴**：识别“工作经历”“授权工作状态”“期望薪资”等不同网站的同义字段。
- **以正确性优先**：字段映射、类型转换和必填校验都可解释、可复核。
- **人始终在环**：插件可以自动填入，但默认不替用户提交申请，不擅自生成不存在的事实。
- **敏感信息可控**：用户可以按网站、字段类型和场景控制哪些资料允许被读取、发送和填写。

### 2.3 产品边界

#### 产品包含

- 结构化个人简历档案的创建、编辑、导出和版本管理。
- 多份求职档案及其与职位/公司的关联。
- 当前网页表单识别、字段语义解析、数据匹配、格式转换和填写预览。
- 必填项检查、冲突提示、低置信度提示和填写结果记录。
- 网站适配规则、用户纠错反馈和可回滚的填写操作。

#### 产品不默认包含

- 自动投递、自动点击“提交申请”或批量申请。
- 自动编造工作经历、学历、证书、薪资或其他个人事实。
- 绕过验证码、登录保护、访问控制或网站安全机制。
- 在用户不知情的情况下收集网页内容或上传完整页面。
- 替代招聘网站自身的账号、隐私或合规机制。

## 3. 使用场景与核心流程

### 3.1 首次建立资料

用户安装插件后，可选择：

- 手工创建个人档案；
- 从另一份已保存档案复制生成新版本。

所有档案数据都由用户在产品内手动创建、填写和确认。产品不支持上传已有简历文件，不提供 PDF/DOCX 解析、OCR 或自动导入，避免未经用户逐项确认的数据进入事实档案。

### 3.2 针对职位准备档案

用户可以从基础档案创建一份求职档案，覆盖基础资料但允许按职位调整：

- 简历语言与格式；
- 个人简介/职业目标；
- 工作经历和项目经历的显示顺序与突出程度；
- 技能关键词；
- 求职城市、职位、薪资和到岗时间；
- 是否展示电话、住址、身份证明、工作授权等敏感字段。

基础档案与职位档案之间采用引用加覆盖的方式。基础数据更新后，系统提示哪些职位档案可以应用更新，而不是静默覆盖用户的定制内容。

### 3.3 填写网页表单

典型流程如下：

1. 用户打开招聘网站的申请页面并选择一个求职档案。
2. 插件读取当前页面中可交互的表单控件及其附近的标签、说明、选项和必填状态。
3. 本地规则先完成已知网站和常见字段的识别；无法确定的字段拆解为原子问题交给 Jev 进行分类、评分或核验。
4. 代码根据 Jev 的结构化决策生成字段映射结果，包括来源数据、目标控件、转换方式、置信度和风险说明。
5. 用户在侧边栏中查看预览，修改或排除字段。
6. 插件按安全顺序写入字段，并监听网页的校验反馈。
7. 系统展示成功、跳过、失败和待人工处理的字段。
8. 用户自行检查并决定是否提交申请。

### 3.4 填写后的复核

插件需支持以下复核方式：

- 仅显示本次即将写入的字段；
- 只填写高置信度字段；
- 标出被转换、截断、合并或存在冲突的字段；
- 一键撤销本次填写；
- 保存本次字段映射和用户修正，作为后续网站适配的反馈。

## 4. 产品能力规划

## 4.1 简历数据维护

### 4.1.1 档案模型

系统至少支持以下信息域：

| 信息域 | 主要内容 | 说明 |
| --- | --- | --- |
| 基础身份 | 姓名、姓名拼音、性别、出生日期、政治面貌、证件号、婚史、民族、籍贯、出生地、生源地、自我评价 | 敏感字段默认不自动填写；旧版快照兼容补齐空值 |
| 联系方式 | 手机、邮箱、所在地、地址、个人网站 | 联系方式可按档案选择 |
| 求职意向 | 目标职位、职能、城市、远程偏好、到岗时间、期望薪资 | 允许多个意向组合 |
| 教育经历 | 学校、学位、专业、起止时间、成绩、描述 | 可设置排序和是否展示 |
| 工作经历 | 公司、职位、地点、起止时间、职责、成果 | 支持在职状态和多种日期格式 |
| 项目经历 | 项目名称、角色、时间、技术栈、背景、行动、结果 | 支持针对职位选择性展示 |
| 技能 | 技能名称、熟练程度、使用年限、关联经历 | 支持同义词和关键词 |
| 证书与资格 | 证书、颁发机构、编号、日期、链接 | 编号属于敏感字段，可单独授权 |
| 作品与链接 | GitHub、作品集、论文、社交主页 | 区分公开和私有链接 |
| 语言能力 | 语言、熟练度、考试成绩 | 支持枚举映射 |
| 其他问答 | 工作授权、是否需要签证、是否有亲属、离职原因等 | 每个字段均需用户确认，不由模型猜测 |
| 补充链接 | 作品集、论文、公开主页等链接 | 由用户手动维护，不作为简历文件解析入口 |

### 4.1.2 数据编辑能力

- 表单编辑、批量编辑、拖拽排序和区块启用/停用。
- 每个字段支持值、语言、来源、更新时间、备注和敏感等级。
- 时间支持年月、完整日期和“至今”，并统一存储为标准形式。
- 枚举字段支持标准值、展示值和网站特定值三层映射。
- 支持字段级撤销、档案级历史版本和版本对比。
- 支持“只读事实”和“职位定制内容”区分，防止职位优化覆盖真实经历。

### 4.1.3 手动维护、导出与备份恢复

所有结构化字段都通过产品内的编辑界面维护，支持单字段编辑、区块编辑、排序、启用/停用、版本对比和撤销。用户输入后即可看到字段格式校验和敏感等级提示。

产品不提供已有简历文件上传、文本粘贴解析、OCR 或自由格式数据导入。产品提供 FastCV 自有备份 JSON 的本地导出和导入，用于用户主动备份与恢复；这不是简历内容解析，也不会把任意 JSON 自动转换成简历档案。

备份 JSON 至少包含格式标识、备份格式版本、导出时间、档案版本、职位档案、用户确认过的站点规则和必要的元数据，不包含模型会话日志、网页原始内容或临时扫描数据。导入时必须：

1. 校验格式标识、版本、结构和完整性；
2. 展示将要新增、覆盖或恢复的档案及版本；
3. 由用户明确选择恢复方式，不静默覆盖当前数据；
4. 在同一个 IndexedDB 事务中完成恢复，失败时整体回滚；
5. 将恢复结果记录为新的本地版本，保留原有历史版本。

备份文件可能包含电话、邮箱、地址和求职意向等敏感信息，导出时必须明确提示用户妥善保存。当前仅支持用户在本机选择 JSON 文件；不接入云盘、不自动上传，也不申请 Google 账号权限。

### 4.1.4 多档案与覆盖关系

推荐采用以下层次：

```text
基础个人档案
├── 中文求职档案
├── 英文求职档案
├── 后端工程师职位档案
└── 海外岗位职位档案
```

每份职位档案记录：基础档案版本、覆盖字段、选中的经历、目标职位上下文和创建时间。系统在使用过期基础版本时必须提示用户，而不是自动替换。

### 4.1.5 隐私和授权

敏感字段至少分为三类：

- **普通资料**：职位、技能、工作经历、教育经历、公开链接。
- **联系资料**：电话、邮箱、地址、个人联系方式。
- **高敏资料**：身份证明、工作授权、签证、薪资、家庭关系等。

用户可以按以下维度授权：

- 是否允许出现在当前职位档案；
- 是否允许填入当前网站；
- 是否允许发送给 Jev；
- 是否允许记录在本地操作日志；
- 是否允许在该网站记住授权。

默认情况下，完整个人档案不发送给模型；只发送完成当前字段匹配所需的最小数据。

## 4.2 网页表单智能填写

### 4.2.1 表单发现

插件需要识别：

- `input`、`textarea`、`select`、自定义下拉框、单选、多选和日期控件；文件上传控件只做识别和提示，不自动上传简历文件；
- 字段的 `label`、`placeholder`、`aria-label`、`name`、`id`、`autocomplete` 和邻近说明文字；
- 必填标记、选项列表、当前值、错误提示和字段可见性；
- iframe、Shadow DOM 或前端框架渲染出的可交互区域（在浏览器权限允许的范围内）；
- 表单所属步骤、当前分页和已展开的可选区块。

扫描结果只保留完成映射所需的结构化字段摘要。默认不把整个 DOM、页面截图或其他无关页面内容发送给模型。

### 4.2.2 字段语义理解

字段识别采用分层策略：

1. **标准属性匹配**：优先使用 `autocomplete`、稳定的字段名和站点适配规则。
2. **本地词典匹配**：识别中英文标签、常见缩写和招聘领域同义词。
3. **上下文匹配**：结合字段所在区块、选项、前后字段和页面步骤。
4. **Jev 原子决策**：对新站点、模糊标签和自定义控件提出预先定义的 `Choice`、`Score` 或 `Noul` 问题，取得候选概率和置信度。
5. **代码组合结果**：由本地程序根据多个独立问题的结果计算最终映射，不把多步业务逻辑塞进一个模型问题。
6. **用户确认与记忆**：用户修正后生成站点或字段级规则，但规则需可查看、可禁用、可删除。

Jev 适合“一个问题、一个判断、一个有限输出”的工作方式。例如，页面字段可以拆成以下独立判断：

```text
Choice: 这个网页字段属于哪个标准字段类型？
Score: 当前页面字段与某个候选资料字段的匹配程度是多少？
Noul: 这段网页说明是否明确要求用户具备工作授权？
```

系统随后在代码中合并这些结果，决定是否展示候选、是否需要确认以及是否允许填写。Jev 返回的 `probabilities` 和 `confidence` 是决策信号，不是绕过风险策略的授权。

Jev 不适合承担以下职责：

- 根据一段职位描述自由生成一份新的简历或求职信；
- 把开放式长文本直接改写成任意结构；
- 输出要由浏览器直接执行的 JavaScript、CSS 选择器或操作脚本；
- 在没有候选集合、评分标准或事实来源时回答开放式问题；
- 替用户生成工作授权、签证、薪资、犯罪记录等事实答案。

这些任务应由用户手动维护、确定性转换器、有限候选集合、业务规则和用户确认共同完成。若未来需要自由文本摘要或职位定制文案，应单独接入具备文本生成能力的模型，并保持与 Jev 决策链路隔离。

Jev 返回的是类型化原子结果，不是下游可以直接执行的网页动作。产品内部的 `FieldMapping` 和 `MappingPlan` 由代码根据这些结果生成，并继续经过来源、目标控件和风险策略校验。以下是应用层的概念示意，不代表 Jev SDK 的原始响应格式：

```json
{
  "jev": {
    "questions": [
      {
        "kind": "choice",
        "name": "field_semantic_type",
        "choice": "work_authorization",
        "probabilities": {"work_authorization": 0.94},
        "confidence": 0.94
      },
      {
        "kind": "score",
        "name": "source_match",
        "score": 0.91,
        "confidence": 0.88
      }
    ]
  },
  "computedByApplication": {
    "sourcePath": "profile.eligibility.workAuthorization",
    "transform": "enum_map",
    "risk": "high",
    "requiresConfirmation": true
  }
}
```

这里的 `computedByApplication` 不是 Jev 生成的内容，而是应用根据候选、规则和风险策略计算出来的执行计划。

### 4.2.3 数据匹配与格式转换

匹配引擎需要处理以下情况：

- 姓名拆分为名、姓，或按网站要求转换顺序；
- 日期从 `YYYY-MM` 转为月/日/年下拉框；
- 工作经历从结构化记录转换为单个富文本框；
- 技能数组映射为标签、逗号分隔文本或多选项；
- 学位、语言熟练度、工作授权等枚举值映射；
- 多个经历映射到重复的经历区块；
- 网站要求回答“是/否”，但资料库中没有确认值；
- 网站限制字数时生成截断预警，而不是静默丢失内容。

转换结果必须保留原始值、目标值、转换规则和是否可逆。无法安全转换时，字段进入人工处理列表。

### 4.2.4 置信度与风险策略

置信度不是唯一的安全依据，还要叠加字段风险等级：

| 场景 | 默认行为 |
| --- | --- |
| 高置信度、低风险 | 可在用户点击“填写”后自动写入 |
| 中置信度、低风险 | 预览中标记，用户确认后写入 |
| 任意置信度、高风险 | 必须逐项确认，不自动选择 |
| 缺少来源数据 | 跳过并提示用户补充 |
| 存在多个候选值 | 不猜测，展示候选值供选择 |
| 可能造成事实改变 | 禁止模型生成，要求用户输入或选择 |

高风险字段包括工作授权、签证、犯罪记录、残障/健康、薪资、离职原因、是否愿意搬迁以及任何法律声明。

### 4.2.5 填写执行

填写执行器应：

- 只操作映射结果中明确授权的目标元素；
- 使用与真实用户交互等价的事件序列，确保 React、Vue 等框架感知到值变化；
- 在写入后读取字段值并进行回读校验；
- 对依赖前置选择动态出现的字段进行分阶段扫描；
- 发现页面校验错误时暂停并定位到对应字段；
- 记录每个字段的成功、失败、跳过和用户修改状态；
- 提供本次操作的撤销能力；
- 永远不默认触发最终提交、发送邮件或不可逆操作。

### 4.2.6 网站适配

网站适配规则分为：

- 通用规则：适用于标准 HTML 和常见招聘字段；
- 站点规则：根据域名、页面特征和字段特征匹配；
- 组织规则：针对某家公司 ATS 的页面流程；
- 用户规则：用户在本地纠正后产生，可单独删除。

规则应使用稳定特征，例如字段语义、标签关系和页面结构。避免只依赖易变的 CSS 类名或随机生成的 DOM ID。站点规则失效时应降级到通用识别，不应阻塞用户手工填写。

## 5. 产品交互与页面

### 5.1 插件弹窗

用于快速查看当前状态和执行常用操作：

- 当前页面是否支持填写；
- 当前使用的求职档案；
- 可识别字段数量、待确认数量和错误数量；
- “扫描页面”“预览填写”“填写已确认字段”“撤销本次填写”等操作；
- 打开资料管理和隐私设置。

### 5.2 侧边栏工作台

侧边栏是核心交互面，分为：

- **字段清单**：字段名称、网页标签、来源值、目标值、置信度、风险和处理状态；
- **问题清单**：缺失、冲突、格式不兼容、无法识别、超长和页面校验失败；
- **预览区**：展示实际会写入网页的内容；
- **控制区**：全选低风险字段、逐项确认、跳过、重新匹配、撤销。

### 5.3 资料管理页

资料管理页支持：

- 档案列表与默认档案；
- 基础档案、职位档案和版本历史；
- 字段搜索、编辑和敏感字段权限；
- 导出、备份恢复和本地数据清除；
- 已学习的网站规则及其删除；
- 模型使用和数据发送记录。

### 5.4 空状态与错误状态

产品必须把“无法识别”解释为可操作的问题，例如：

- “未找到可编辑的表单，请进入申请步骤后重试”；
- “发现 3 个字段可能是工作授权，因缺少确认值已跳过”；
- “该字段有两个候选经历，请选择后继续”；
- “网页已拒绝该值，请检查格式或手工修改”。

禁止只显示“AI 失败”“未知错误”而不给出恢复路径。

## 6. 技术架构

### 6.1 总体架构

```text
┌────────────────────────────────────────────────────────────┐
│                       浏览器扩展                            │
│                                                            │
│  Popup / Side Panel                                        │
│        │                                                   │
│        ▼                                                   │
│  Extension Controller ──────── Session & Permission Guard  │
│        │                         │                         │
│        ├── Profile Store         ├── Audit / Undo Store     │
│        ├── Mapping Engine        └── Site Rule Store       │
│        │                                                   │
│        ├───────────────┬────────────────┐                  │
│        ▼               ▼                ▼                  │
│  Content Script   DOM/Form Adapter   Page Bridge            │
│        │                                                   │
│        ▼                                                   │
│  当前招聘网站页面                                            │
└────────┬───────────────────────────────────────────────────┘
         │ 最小化、脱敏、结构化请求
         ▼
┌────────────────────────────────────────────────────────────┐
│             Jev Decision Gateway（可替换决策层）            │
│  状态裁剪 · 类型化问题 · 置信度策略 · 限流 · 重试 · 审计     │
└────────────────────────────────────────────────────────────┘
```

### 6.2 浏览器扩展组成

#### Extension Controller

负责扩展内部的状态机和消息路由，不直接操作 DOM。主要职责：

- 管理当前页面会话和所选求职档案；
- 调度页面扫描、模型匹配、预览、填写和撤销；
- 校验跨上下文消息的来源、会话 ID 和权限；
- 保证一次只存在一个可恢复的填写事务。

#### Popup / Side Panel

负责用户交互，不保存业务真相。所有资料和映射结果通过受控接口读取，并根据字段风险显示不同的确认方式。

#### Content Script

运行在招聘网页上下文中，负责：

- 发现和规范化表单控件；
- 收集页面字段摘要；
- 执行经过授权的填写操作；
- 回读填写结果和页面校验信息；
- 处理动态表单的增删和分页变化。

Content Script 不应访问扩展私有密钥，不应直接调用外部模型服务。

#### Form Adapter

将不同页面控件统一为内部接口，例如：

```text
scan() -> FieldSnapshot[]
read(fieldId) -> FieldValue
write(fieldId, value) -> WriteResult
validate(fieldId) -> ValidationResult
undo(transactionId) -> UndoResult
```

常见控件和复杂站点可以通过 Adapter 扩展支持，但 Adapter 只能执行白名单动作。

#### Profile Store

本项目没有服务器，且用户资料以手动维护的结构化字段为主。推荐使用浏览器原生 **IndexedDB** 作为档案主库，不引入 SQLite：IndexedDB 同样是浏览器内置能力，但提供异步事务、对象存储、索引和数据库 Schema 版本升级，更适合保存多版本档案。[MDN IndexedDB 文档](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)

`chrome.storage.local` / `browser.storage.local` 只保存少量扩展设置和功能开关，不承担档案版本库职责；当前档案指针必须和版本快照一起放在 IndexedDB 事务中；`storage.session` 或内存保存当前页面的临时扫描结果和模型上下文。

建议通过 `ProfileRepository` 隔离业务层和浏览器 API：

```text
ProfileRepository
├── profiles           档案身份、名称、类型、当前版本指针
├── profileVersions    不可变的完整档案快照
├── profileDrafts      用户正在编辑的草稿和自动保存状态
├── siteRules          用户确认过的站点规则
├── fillTransactions   最近少量填写事务，用于撤销和诊断
└── metadata           数据库版本、迁移状态、备份时间
```

### 档案版本模型

简历档案数据量小，采用“完整快照”比复杂的差分存储更容易保证正确性：

- 用户编辑时先更新 `profileDrafts`，避免每次输入都产生正式版本；
- 用户点击“保存版本”时，把当前草稿写入 `profileVersions`，生成不可变的 `versionId`；
- `profiles.currentVersionId` 指向当前使用版本；
- 历史版本只读，可查看差异、复制为新草稿或恢复为新版本；
- 恢复不会覆盖旧版本，而是创建一个新的版本并移动当前指针；
- 每个职位档案记录所基于的基础档案版本，基础档案更新时提示用户重新应用，不静默覆盖；
- 单个档案默认保留有限数量的版本，例如最近 50 个，用户可手动删除旧版本。

一次正式保存必须在同一个 IndexedDB `readwrite` 事务中完成：写入版本快照、更新当前版本指针和清理过期草稿要么全部成功，要么全部失败。这样可以避免出现“版本已创建但当前指针未更新”的半成功状态。IndexedDB 的数据库结构升级和对象存储变更通过 `versionchange` / `onupgradeneeded` 处理，数据库 Schema 版本与用户简历版本是两套独立概念。[MDN IndexedDB 使用说明](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB)

### 持久化和丢失边界

浏览器官方说明中，扩展的 IndexedDB 和其他扩展存储不会因为用户普通清理浏览历史/缓存而自动清除，但仍可能在存储压力下被逐出；用户主动清除扩展数据、卸载扩展、浏览器配置损坏或设备故障仍可能导致数据丢失。首次保存档案后可以调用 `navigator.storage.persist()` 请求持久化，并在设置页显示是否获准，但不能把它当作备份保证。[Chrome Storage and Cookies 文档](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies)

因此，产品必须提供用户主动触发的完整 JSON 备份导出和恢复，并在扩展卸载/清除数据提示中明确告知用户。当前只接受 FastCV 自己导出的备份 JSON，不接受任意简历文件或自由格式 JSON。

未来如果接入 Google Drive 等 Google 存储，应复用同一份版本化备份 JSON 和校验协议，只新增云端存储适配器：本地数据模型、版本模型和恢复流程不改变。云端能力必须是用户主动开启的可选能力，单独申请 OAuth 权限，并明确展示文件存放位置、同步范围和冲突处理方式。

### 访问隔离与隐私

- 业务层只通过 `ProfileRepository` 读写，不直接调用浏览器存储 API；
- Content Script 不直接读取 IndexedDB 或完整档案，只通过消息向 Extension Controller 请求当前填写所需的最小字段；
- 不使用网页 `window.localStorage` 保存扩展资料；Content Script 访问网页存储时可能读到宿主页面的存储；
- 当前填写会话、临时扫描结果和模型请求上下文任务结束后清理；
- 浏览器存储不是操作系统级安全保险箱。高敏字段默认不发送给 Jev、不进入普通日志；若未来增加用户密码解锁和 Web Crypto 加密，必须提示没有服务器时忘记密码无法恢复；
- 不使用 `storage.sync` 保存简历数据，它适合少量非敏感偏好，不适合作为本项目的跨设备同步方案。

#### Mapping Engine

负责把页面字段和资料字段转换成可执行的 Mapping Plan。它包含：

- 本地标准字段词典；
- 日期、枚举、数组、文本和长度转换器；
- 通用/站点/用户规则的优先级；
- Jev `Choice` / `Score` / `Noul` 结果合并和内部类型校验；
- 置信度、字段风险和人工确认策略。

模型不得直接返回“执行动作列表”并由扩展无条件执行。扩展必须把 Jev 的类型化决策转换为内部计划，再通过来源、目标控件和动作白名单校验。

### 6.3 Jev 决策层

Jev 通过统一 Gateway 接入，扩展不直接依赖具体服务供应商的请求格式。Gateway 不是通用 LLM Prompt 代理，而是把业务状态转换为有限、可审计的类型化问题，再把类型化决策交给本地工作流组合。由于 Jev 仍处于早期开放阶段，Gateway 还需要维护能力版本和降级开关，避免把供应商当前的返回能力直接固化到产品业务层。Gateway 提供：

- 状态裁剪和字段级授权；
- `Choice`、`Score`、`Noul` 问题定义与版本管理；
- 候选集合、评分标准和问题数量的上限控制；
- 类型化返回值、概率分布和置信度的校验；
- 超时、重试、限流和成本控制；
- 模型版本、问题定义版本和工作流版本记录；
- Jev 不可用时降级到本地规则，不用另一个自由文本模型静默替代；
- 不保存原始个人资料或按用户选择保存短期调试样本；
- 对决策结果进行来源、字段风险和允许动作检查。

#### Jev 适合处理的任务

- 在有限标准类型集合中选择网页字段语义；
- 对页面字段与多个资料字段候选分别评分，再由代码排序和设定阈值；
- 在有限选项集合中匹配页面选项与标准枚举；
- 判断字段是否具有高风险、是否需要人工确认；
- 判断网页错误或说明是否对应某个预定义状态；
- 对候选映射、页面上下文和资料来源进行一致性核验。

Jev 的工作流应拆成多个相互独立的原子问题，并在代码中组合。不能用一个开放式问题同时要求模型识别字段、选择资料、转换格式、判断风险和决定是否写入。

#### Jev 不应处理的任务

- 凭空生成用户经历或资质；
- 生成简历段落、求职信或其他自由文本；
- 解析或导入简历文件；
- 自主决定是否回答法律/隐私/授权问题；
- 直接点击提交、发送邮件或执行任意脚本；
- 绕过验证码、反爬或权限限制；
- 在没有用户授权时读取或上传页面内容。

若产品未来需要职位描述摘要或简历文案改写，应引入独立的文本生成能力，并通过“仅使用已确认事实”的输入、输出审核和用户确认与 Jev 决策链路隔离。不能因为两者都被称为 AI 就共享同一执行接口。

### 6.4 数据流

#### 扫描和匹配流

```text
页面表单
  → Content Script 采集字段摘要
  → 本地规则匹配
  → 仅将未确定字段和必要上下文交给 Jev
  → 类型化结果校验与风险标注
  → 结合本地档案生成 Mapping Plan
  → 侧边栏预览
```

#### 填写流

```text
用户确认
  → 权限/档案版本校验
  → 按依赖顺序执行低风险字段
  → 动态重新扫描
  → 写入高风险字段前逐项确认
  → 回读与网页校验
  → 记录事务并提供撤销
```

### 6.5 内部数据模型

建议建立以下核心实体：

```text
Profile
  id, name, locale, baseProfileId, version, sections, visibilityPolicy

ProfileField
  path, value, valueType, source, sensitivity, verifiedAt, updatedAt

JobProfile
  id, profileId, targetRole, targetCompany, overrides, selectedSections

PageSession
  id, tabId, origin, pageFingerprint, profileId, createdAt, status

FieldSnapshot
  id, sessionId, selectorHint, label, type, options, required, context

FieldMapping
  fieldId, sourcePath, transform, confidence, risk, reason, status

FillTransaction
  id, sessionId, mappingPlanVersion, beforeValues, afterValues, status

SiteRule
  scope, matchPattern, ruleVersion, mappings, enabled, userOwned

AuditEvent
  id, eventType, actor, fieldRefs, result, createdAt, retentionPolicy
```

其中 `selectorHint` 只能作为页面操作的辅助信息，不能成为跨页面永久信任的唯一标识。`beforeValues` 需要按敏感等级加密或采用受限保留策略，以支持撤销而不扩大隐私暴露面。

### 6.6 浏览器权限与安全边界

权限遵循最小化原则：

- 仅在用户触发功能或已授权的网站上访问页面内容；
- 不申请与填写功能无关的历史记录、下载、标签页或所有网站权限；
- 模型 API 密钥不放在扩展前端；
- 外部请求使用 HTTPS，并校验响应格式；
- 跨上下文消息使用来源、会话和动作白名单校验；
- 页面内容视为不可信输入，防范提示注入、恶意字段标签和伪造扩展消息；
- 站点规则和模型返回值都不能动态生成任意代码执行路径；
- 本地档案、导出文件、日志和缓存都要有明确的清理入口。

## 7. 规则、模型与人工判断的职责边界

```text
确定性规则：标准字段、常见格式、已验证站点适配、权限检查、最终阈值与写入策略
        ↓
Jev：原子语义分类、候选评分、有限选项选择、状态核验
        ↓
产品策略：风险分级、是否需要确认、是否允许写入
        ↓
用户：确认事实、处理歧义、决定是否提交
```

任何模型输出在进入网页前都必须经过四道检查：

1. 输出结构是否符合 Schema；
2. 来源字段是否存在且属于当前档案；
3. 转换是否符合目标控件类型和长度约束；
4. 风险等级是否要求人工确认。

## 8. 非功能需求

### 8.1 正确性

- 所有自动填写值都能追溯到用户档案字段或用户确认的转换结果。
- 不确定字段不得以高置信度展示。
- 页面回读值必须与目标值一致，或明确标记为网站格式化后的结果。
- 填写失败必须是局部失败，不能导致已保存档案损坏。

### 8.2 性能

- 已知网站和本地规则优先即时展示初步匹配。
- 侧边栏应在扫描结束后先展示字段，再逐步补充模型结果。
- 模型请求按字段组批处理，避免为每个字段单独请求。
- 模型不可用时仍能使用本地规则完成基础填写。

### 8.3 可用性

- 第一次使用无需理解 HTML、ATS 或模型概念。
- 每个自动动作都说明“填入什么、来自哪里、为什么这样匹配”。
- 所有自动填写都可撤销。
- 手工修改不会在没有提示的情况下被下一次扫描覆盖。

### 8.4 隐私与合规

- 默认本地优先，最小化上传，明确展示模型调用范围。
- 用户维护的简历数据和高敏字段不得进入普通日志。
- 支持清除本地资料、模型会话、网站规则和操作记录。
- 隐私政策应说明页面读取、模型处理、保留期限和第三方服务。
- 对不同国家/地区的工作授权、平等就业和敏感个人信息问题提供可配置的人工确认策略，不由模型替用户作答。

### 8.5 可维护性

- 字段语义、转换规则、站点适配、Jev 问题定义和决策工作流均可版本化。
- 产品逻辑与具体模型供应商解耦。
- 站点规则失效不应影响资料管理能力。
- 规则、模型和执行器产生的错误应分层记录，便于定位是识别、映射、转换还是网页交互失败。

## 9. 质量度量

产品质量不应只用“填写成功率”衡量，至少需要同时关注：

- 字段识别准确率；
- 来源映射准确率；
- 高风险字段误填率；
- 页面回读一致率；
- 用户撤销率和人工修改率；
- 缺失数据被正确跳过的比例；
- 未经授权的数据发送事件数；
- 模型不可用时的本地降级成功率；
- 站点规则失效后的恢复率。

其中，高风险字段误填和未经授权的数据发送属于阻断性质量问题，不能被普通成功率抵消。

## 10. 典型验收场景

### 场景 A：常见英文申请表

用户选择英文求职档案，插件识别姓名、邮箱、电话、教育和经历字段，完成低风险字段填写；工作授权字段要求单独确认；用户可以预览并撤销。

### 场景 B：动态添加多段工作经历

插件识别第一段经历后，根据页面的“Add another experience”控件增加后续区块，按用户选中的经历顺序填写，并在每一段写入后回读校验。

### 场景 C：字段含义不明确

页面出现“Are you legally authorized to work...”。如果用户档案没有已确认值，插件显示待处理，不调用模型生成答案，也不代替用户勾选。

### 场景 D：字数限制

职位描述字段限制 500 字符，而用户项目描述更长。系统展示原文和可选的压缩结果；压缩只能基于已有内容，且必须由用户确认后写入。

### 场景 E：模型不可用

Jev Gateway 超时或不可用时，已验证的站点规则和本地字段词典仍然可用；无法确定的字段被列为待人工处理，不能静默跳过或错误填写。

### 场景 F：网页结构变化

站点规则无法定位目标字段时，插件降级到通用字段扫描，并向用户说明适配规则可能已失效；用户可以手工填写并选择是否保存新的本地规则。

## 11. 产品决策原则

1. **事实优先于自动化**：没有用户来源的数据不自动生成。
2. **确认优先于猜测**：尤其是法律、授权、薪资和个人敏感信息。
3. **本地优先、最小披露**：能在浏览器本地完成的识别和转换，不发送给模型。
4. **可解释、可回滚**：用户知道每个值来自哪里，并能撤销本次填写。
5. **规则优先、模型补足**：确定性问题不交给模型，模型只处理语义不确定性。
6. **网站变化可容错**：适配规则失效时保留基础能力和人工路径。
7. **不把提交当作填写**：产品核心是正确准备和填充数据，最终提交始终由用户决定。
